# maintenance/ —— 维护者文档（不属于技能运行时）

**这个目录里的文件是给维护这个仓库的人看的，不是给做任务的 agent 看的。**

## 为什么单独放

设计原则（v2.1.0 起执行）：**skill 里只留运行时内容——做任务时会用到、会改变当次决策的东西。** 给 skill 打分、规划怎么改 skill、让 skill 自我进化，都属于维护时职能。它们留在 skill 里有三个害处：

1. **占上下文**：技能被触发加载时，每个 token 都在和任务内容竞争注意力；
2. **抢触发**：导航与说明里每多广告一个职能，就多一组可能把 agent 带去做元工作的词；
3. **混受众**：做任务的 agent 和维护者是两种读者，混在一起两边都读不好。

业界做法一致：Anthropic 把评估放在独立的元技能（skill-creator）里、结果放技能目录的同级 workspace；Trail of Bits 把贡献与校验规范写在仓库根的 AGENTS.md、测试由 CI 跑；SkillOpt 是外部优化器，部署时只导出成品技能。**优化与评估永远从外部作用于 skill，不住在 skill 里面。**

## 规则

- `SKILL.md` 不引用本目录任何文件；技能的导航、目录树、description 都不出现它们。
- 本目录文件之间可以互引；引用运行时文件时用其现行路径（`methodology/…`、`prompts/…`）。
- 新的维护类文档（评分、规划、复盘、进化流程）一律放这里，不进 `methodology/`。
- 运行时发现需要改 skill 时，做任务的 agent 只记录问题（按 `methodology/25-claim-gates.md` 的状态标注），改动留到维护环节处理，不在任务中途动 skill。
