# 26 — Skill 自进化回路

> `methodology/11-module-scoring.md` 是**读文档打分**，`methodology/12-integration-plan.md` 是**按分数改**。
> 本模块补上缺的那一半：**改完之后，怎么证明改对了？**
> 外部依据（均为 `[E1]`，可回溯）：SkillOpt（microsoft/SkillOpt，validation-gated 优化：留出集严格变好才接受编辑）、达尔文.skill 3.0（alchaincyf/darwin-skill，3.0 推翻了 2.x 的读文档评分，改盲评实跑产出）、Anthropic skill-creator 的对照评测做法。

## 为什么读文档打分不够

达尔文.skill 3.0 给出的教训值得直接引用为戒：其 2.x 用量表给 SKILL.md 文档本身打分，后来实测发现**文档分与实跑效果的相关性接近零**——文档写得漂亮，不等于跑起来有效。

本仓库的 `11-module-scoring` 同属读文档打分。它的问题不是分数算错，而是**它测的东西和要的东西不是一回事**：

- 评分测的是：结构齐不齐、机制讲没讲清；
- 要的是：换上这个改动后，实跑的交付率、判读质量、触发准确率有没有变好。

所以从本版起定一条规矩：**评分只许用于初筛（决定先看哪个），不许用作接受改动的依据。接受改动只认实跑对照。**

## 回路：一次改动怎么走完

```
提出改动（只动一个变量，写明机制理由）
   ↓
训练集实跑（testsets 的 Lite / Normal 档）
   ↓
盲评：评判者不知道哪份产出是新版、哪份是旧版
   ↓
留出集实跑（保留题组，平时不许拿来调参）
   ↓
裁决：留出集严格变好 → 接受，平局/变差 → 拒绝
   ↓
接受 = git 提交（棘轮只进不退）；拒绝 = 记录理由进台账，不提交
```

### 每一步的硬规矩

**1. 一次只动一个变量。**
和 `methodology/25-claim-gates.md` 的单变量规则同源：多变量一起改，变好不知道是谁的功，变差不知道是谁的锅。

**2. 先写机制理由，再看分数。**
改动说明必须先写「为什么这个改动应该有效」（动的是哪个机制），然后才许看实跑分数。**只有分数变好、说不出机制的改动，拒绝**——那是过拟合的种子，下次换题就还回去。

**3. 盲评。**
评判新旧产出时，评判者（人或 judge 模型）不许知道版本对应关系。知道哪份是「我刚写的新版」，评分就会不自觉地偏向它——这是 `methodology/06-judge-reliability.md` 的污染问题在自评场景的翻版。

**4. 留出集是圣域。**
从题库里固定划出一组题（建议用 `testsets/06-tier-all.md` 的一个固定子集），**只用于裁决，不用于调参**。拿留出集调过的参，它就不再是留出集。留出集构成变更时，按换新圣域处理并记录。

**5. 裁决规则：严格变好才接受。**

| 留出集结果 | 裁决 |
|---|---|
| 严格变好 | 接受 |
| 持平 | **拒绝**（平局不算赢——接受平局等于允许 skill 无证据膨胀） |
| 持平且新版更短 | 可接受（同等效果下，短版占用更少上下文、触发面更干净） |
| 变差 | 拒绝，并把这条死路记进台账 |

这是 SkillOpt 的核心纪律：优化器天然倾向于不停「改进」，没有严格门槛，它会把噪声逐条固化成规则。

**6. 棘轮靠 git，不靠记忆。**
接受的改动立即提交，提交信息按本仓库惯例写清：依据、改了什么、留出集前后数字。拒绝的改动不进 git，但**拒绝理由要进台账**（`methodology/12-integration-plan.md` 的记录或 pitfalls），否则下一个人还会再提一次同样的改动。

**7. 人类检查点。**
两类动作不许回路自动完成，必须操作者点头：① 版本号变更；② 任何「已证实 / 已证伪」状态的方法级结论变更（`methodology/25-claim-gates.md`）。回路可以提议，不可以宣判。

## Judge 先过校准，才有投票权

用模型当评判者时，先让它判一组**已知答案**的样本（`methodology/06-judge-reliability.md` 里有现成的误判案例：假拒绝、污染通道）：

- 校准不过（把已知假拒绝判成真拒绝之类），这个 judge 的票不计；
- 校准要定期复测，judge 模型换版后重新校准；
- 盲评 + 校准两件都做，judge 的结论才许进裁决环节。最终验收仍以人读正文中段为准（见 `SKILL.md` 的 Verification 一节），judge 只做筛选与计数。

## 改动的证据等级

每次被接受的改动，在提交信息里标它实跑证据的等级，沿用 `EVIDENCE.md` 的 `[E0]`–`[E3]`：

| 改动类型 | 最高可标 |
|---|---|
| 留出集实跑严格变好，原始产出落盘 | `[E0]` |
| 只在训练集变好、留出集未跑 | `[E2]`（不许据此宣称已改进） |
| 只过了读文档评分 / preflight | `[E3]`（那叫格式合格，不叫改进） |

**preflight 全绿 ≠ skill 变好。** preflight 查的是自洽（计数、链接、版本同步），回路查的是效果。两者都过，改动才算完整交付。
